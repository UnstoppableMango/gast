## Required Changes

### 1. Round-trip fidelity MUST is unresolvable as written for go/ast-derived languages

§2.3: "Round-trip fidelity to source text MUST be achievable from a gast representation without loss."

`go/ast` stores byte-offset positions (`token.Pos`) but does not store whitespace tokens, blank lines, or formatting between nodes. To achieve lossless round-trip from a `go/ast`-derived gast tree you would need to re-read the source file and correlate positions back to raw bytes — effectively a second lexer pass. This is not a minor gap to document; it means the Go language extension cannot satisfy the MUST requirement by deriving from `go/ast` alone.

Two honest paths:
- **Downgrade:** Change the MUST to "SHOULD" for languages where upstream source is an AST rather than a CST, and document per-language round-trip fidelity grade in the extension schema.
- **Strengthen:** Require Go language extension to supplement `go/ast` with a raw token stream (e.g., `go/scanner` output) correlated by position, stored alongside the derived AST nodes. This achieves the MUST but is a significant implementation cost.

Pick one and document it. The current text promises MUST but the execution path for Go contradicts it.

### 2. `google.protobuf.Any` runtime descriptor requirement is unaddressed

§3.2 uses `repeated google.protobuf.Any extensions` on every node. Unpacking an `Any` field requires the consumer's protobuf runtime to have the message descriptor registered. In generated Go, this is automatic if the package is imported. In other languages, it may not be. For dynamically-loaded extension types (a third-party `NixLambdaPattern` the generator has never seen), there is no unpacking path without pre-compilation or dynamic reflection.

The doc says "consumers check the URL, unpack or ignore" but does not define how a consumer accesses the descriptor for an extension type they depend on. This needs an explicit answer:
- Do consumers import the extension proto package and get descriptors for free?
- Is there a descriptor-set distribution mechanism?
- Are unknown extension types always opaque bytes to non-owning consumers?

The third option is fine and consistent with the "ignore unknown extensions" contract — but it needs to be stated explicitly so implementers know not to design for dynamic reflection.

## Major

### 3. `oneof` versioning creates exhaustive-switch fragility

§3.3: interface/union types map to `oneof` wrapper messages. In proto3, adding a new field to a `oneof` is wire-compatible (old decoders see an unknown field). But many language generators and consumers write exhaustive switches over `oneof` cases. A new node kind in Go 1.N breaks those switches at compile time (Go, Rust) or silently at runtime (weakly-typed languages).

Document this explicitly in §5.3 (Compatibility) and in the extension schema template. Recommend that generated SDKs include a `default`/`unknown` case in switch helpers, and that the extension changelog call out `oneof` additions as soft-breaking changes that consumers must handle defensively.

### 4. Well-known namespace promotion: no governance

§3.2: "Well-known types SHOULD NOT be defined until a concept is observed in two or more language implementations." Who decides? What is the process — a PR, an issue, a vote? Without a governance note, "well-known" will be contentious in practice. Even one sentence ("a maintainer opens a proposal issue; merged after 14-day review") is enough.

### 5. Fan-out UC-5 implies storage with no defined model

UC-5 uses `AST store` as a box in the pipeline diagram. gast has no storage format, no addressing scheme, and streaming is deferred. The use case is realistic and the fan-out pattern is compelling, but as written it implies consumers will solve storage themselves (a file path, object storage, etc.). Make this explicit: gast has no opinion on AST storage; consumers are responsible for the store layer. One sentence in UC-5 prevents future scope creep.

## Minor

### 6. UC-3 filename inconsistency

UC-2 output is `foo.ts.gast.bin` (TypeScript gast binary). UC-3 input is `foo.ts.gast.bin` but the command is:

```sh
cs-to-ts foo.cs.gast.bin | ts-generator > foo.ts
```

The input file is `foo.cs.gast.bin` (C# gast binary), not `foo.ts.gast.bin`. The mermaid diagram and the command disagree. Fix the command or the diagram.

### 7. §5.5 common path is fragile for Go

Go ships AST changes in minor versions (go1.21, go1.22, etc.). "A maintainer manually reviews upstream AST changes introduced by the version bump" is a human reading Go release notes for every minor release. Over a multi-year horizon this will be missed. The update cadence section should recommend at minimum a CI job that diffs the public API surface of `go/ast` against the previous pinned version (e.g., `go doc` diffing, or comparing the exported type set). Even if the common path stays manual, add a lint/CI hook to flag when the upstream version bumps without a corresponding extension schema bump.

### 8. No proto package namespace defined

§3.2 hints at `gast.core.v1.*` as a well-known namespace but the proto package declaration is never specified. Before any code generation, define: proto package name (`gast.core.v1`), Go package path (`github.com/UnstoppableMango/gast/proto/core/v1`), and how extension packages are namespaced (`gast.lang.go.v1`, etc.). This is a one-time decision with large downstream impact on import paths in every generated SDK.

### 9. Nix lazy evaluation gap should be quantified

§2.3 and §2.2 correctly exclude type inference and runtime evaluation. Nix's specific problem is that `with` expressions, `inherit`, attribute set merging, and `import` semantics mean that even the *structure* of a Nix AST depends partly on evaluation context. The doc says "best-effort and documented as such" — this is honest, but the Nix extension schema should explicitly enumerate which Nix constructs are representable statically and which are not (e.g., `builtins.import` paths are opaque; `with` scopes cannot be resolved without evaluation). Without this, parser authors will make inconsistent choices.

## Suggested Additions

1. **Proto schema sketch** — Even a 20-line `.proto` fragment showing `Node`, `SourceSpan`, and one language extension message would validate the `Any`-extension model against actual protobuf constraints and expose any design gaps before implementation. Include it as `docs/schema-sketch.proto` or inline in §3.1.

2. **Round-trip fidelity matrix** — A table mapping each target language to its fidelity grade: full CST (Nix, if bespoke parser), position-only (Go via `go/ast`), best-effort. Sets consumer expectations and makes the MUST/SHOULD distinction per-language explicit.

3. **Extension authoring guide skeleton** — §3.2 and §5.4 define the contract for extensions. A stub template (required fields, manifest format, `min_core_major` declaration location) would reduce friction for the first non-core extension author and make the compatibility contract concrete.
